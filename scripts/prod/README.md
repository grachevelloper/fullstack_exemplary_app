# Production-скрипты: как устроен деплой на VPS

Эта папка содержит не «скрипты Timeweb», а команды проекта для **обычного VPS с Docker**. Они рассчитаны на корневой [`docker-compose.yaml`](../../docker-compose.yaml): PostgreSQL, Nest backend, React frontend и Nginx работают как отдельные контейнеры на одном сервере.

> Это не конфигурация Timeweb App Platform. Там запрещены `volumes` и порты `80`/`443`; эти скрипты нужно использовать на VPS/VDS, где у нас есть SSH и установлен Docker.

## Карта файлов

| Файл | Когда запускать | Задача |
| --- | --- | --- |
| [`bootstrap-tls.sh`](./bootstrap-tls.sh) | Один раз, перед первым HTTPS-деплоем | Поднимает сайт по HTTP, получает сертификат Let's Encrypt, затем включает HTTPS. |
| [`deploy.sh`](./deploy.sh) | После каждого `git pull` с новой версией | Собирает backend/frontend, создаёт бэкап, применяет миграции, перезапускает приложение и проверяет его готовность. |
| [`renew-tls.sh`](./renew-tls.sh) | По cron, например раз в день | Продлевает сертификаты и перезагружает Nginx только если сертификат изменился. |
| [`restore-backup.sh`](./restore-backup.sh) | Только при аварийной проверке восстановления | Скачивает дамп из S3 и восстанавливает его **в отдельную БД**. |
| [`../../ops/backup/backup.sh`](../../ops/backup/backup.sh) | Обычно запускается из `deploy.sh` или cron | Делает PostgreSQL-дамп, загружает его в S3 и удаляет старые копии по правилам хранения. |
| [`../../ops/backup/Dockerfile`](../../ops/backup/Dockerfile) | При сборке backup-сервиса | Создаёт маленький образ с `pg_dump`, `pg_restore` и AWS CLI. |

## Что должно быть на VPS

Перед первым запуском нужны:

1. Linux VPS (например, Ubuntu 24.04), SSH-доступ и публичный IP.
2. Установленные Docker Engine и Docker Compose plugin: команда `docker compose version` должна работать.
3. Клонированный репозиторий. Скрипты запускаются **из корня репозитория**, потому что вызывают `docker compose` без `-f`.
4. Файл `.env`, созданный на сервере из `.env.example`, с настоящими секретами и доменом. Его не коммитим и не отправляем в чат.
5. DNS-запись домена `A`, указывающая на IP VPS, до запуска `bootstrap-tls.sh`.

Минимальный поток работы после начальной настройки:

```sh
# На своём компьютере
git add <нужные файлы>
git commit -m "..."
git push

# На VPS, в папке репозитория
git pull
sh scripts/prod/deploy.sh
```

Файлы не нужно загружать вручную: их переносит Git. Скрипт не делает `git pull` сам специально — так деплой не сможет неожиданно забрать незнакомый коммит.

## Модель Compose: что именно запускается

В [`docker-compose.yaml`](../../docker-compose.yaml) описаны сервисы:

```text
Интернет
   │  80/443
   ▼
 nginx ──► frontend (статические файлы)
   │
   └────► backend ──► db (PostgreSQL)

tools profile: migration, backup
```

- `db` хранит данные в именованном Docker volume `postgres_data`. Обычный `docker compose down` volume не удаляет; `docker compose down -v` удалит его вместе с данными БД.
- `backend` ждёт, пока `db` станет healthy.
- `frontend` ждёт healthy backend.
- `nginx` — единственный сервис с портами `80` и `443` на хосте.
- `migration` и `backup` имеют профиль `tools`, поэтому не стартуют постоянно при обычном `docker compose up`.

## Базовый Shell: конструкции, которые встречаются в скриптах

### `#!/usr/bin/env sh`

Это *shebang* — строка, по которой ОС понимает, чем исполнять файл, если запустить его напрямую (`./scripts/prod/deploy.sh`).

- `sh` — переносимый POSIX-совместимый shell. Это не обязательно Bash.
- `/usr/bin/env sh` находит `sh` через `PATH`, а не привязывается к конкретному пути вроде `/bin/sh`.
- Скрипты можно запускать и так: `sh scripts/prod/deploy.sh`. Тогда shebang не участвует: ты явно передал интерпретатор.

### `set -eu`

Это строгий режим выполнения, включённый в каждом shell-скрипте.

- `-e`: остановиться, если команда вернула ненулевой код. Например, не продолжать деплой после неудачной миграции.
- `-u`: считать обращение к неустановленной переменной ошибкой. Это защищает от команд с пустым паролем или путём.

Это не абсолютная защита: в конструкциях `if`, `&&`, `||` и некоторых подстановках код возврата имеет особые правила. Поэтому команды всё равно нужно читать и не заменять их «на глаз».

### Переменные: `${NAME:-default}` и `${NAME:?message}`

```sh
CERTBOT_IMAGE="${CERTBOT_IMAGE:-certbot/certbot:v5.7.0}"
: "${LETSENCRYPT_EMAIL:?LETSENCRYPT_EMAIL must be set}"
```

- `${NAME:-значение}`: взять `NAME`, если она задана и не пуста; иначе использовать значение после `:-`. Это дефолт, который можно переопределить окружением.
- `${NAME:?текст}`: если `NAME` пуста или не задана, немедленно напечатать текст и остановить скрипт.
- `:` — встроенная shell-команда «ничего не делать». Здесь она нужна только для вычисления и проверки `${...}`.

Например, перед восстановлением бэкапа обязательны `RESTORE_S3_KEY` и `RESTORE_DB_NAME`: без них скрипт не начнёт потенциально опасную операцию.

### Кавычки, `$`, `$(...)` и перенос строки

```sh
rollback_tag="rollback-$(date -u +%Y%m%dT%H%M%SZ)"
```

- `$NAME` — значение переменной.
- `$(команда)` — выполнить команду и подставить её stdout. Здесь `date` создаёт UTC-метку, например `rollback-20260803T090558Z`.
- Двойные кавычки сохраняют пробелы внутри значения и всё ещё позволяют `$NAME`/`$(...)` раскрываться. Поэтому пути и переменные почти всегда пишутся как `"$path"`.
- Одинарные кавычки, например `'fetch(...)'`, передают текст буквально. Это важно, когда внешний shell не должен раскрывать `$` до передачи команды в контейнер.
- `\` в конце строки означает: команда продолжается на следующей строке. Это только форматирование для читаемости.

### Условия и циклы

```sh
for service in backend frontend; do
    # тело цикла для каждого имени
done

if [ -n "$image_id" ]; then
    # выполнить, если строка непустая
fi
```

- `for ... in ...; do ... done` повторяет блок для каждого слова списка.
- `[ ... ]` — команда `test`; `-n` означает «строка непуста», `-f` — «существует обычный файл», `=` — сравнение строк.
- `>&2` перенаправляет сообщение в stderr. Так ошибки можно отделить от обычного вывода.
- `exit 1` немедленно завершает скрипт с ошибкой.

### Временные файлы и `trap`

```sh
backup_dir=$(mktemp -d)
trap 'rm -rf "$backup_dir"' EXIT
```

`mktemp -d` создаёт уникальную временную папку. `trap ... EXIT` обещает удалить её при любом выходе из скрипта — успешном или из-за `set -e`. Это важно, чтобы дампы с БД не оставались на диске VPS.

## `bootstrap-tls.sh`: первый HTTPS-запуск

Этот скрипт нужен после создания `.env` и DNS-записи. Запуск:

```sh
sh scripts/prod/bootstrap-tls.sh
```

Последовательность:

1. Проверяет `NGINX_SERVER_NAME` и `LETSENCRYPT_EMAIL`.
2. Выбирает дефолты для образа Certbot и путей:
   - `CERTBOT_WWW_PATH=./certbot/www` — папка HTTP challenge;
   - `LETSENCRYPT_PATH=/etc/letsencrypt` — папка сертификатов на VPS.
3. `mkdir -p` создаёт эти папки; `-p` не считает ошибкой уже существующую папку.
4. `docker compose up -d db` запускает только PostgreSQL в фоне.
5. `docker compose --profile tools run --rm migration` применяет миграции. Сервис `migration` создаётся на один запуск и удаляется после него.
6. Временно запускает backend/frontend/nginx с HTTP-конфигом:

   ```sh
   NGINX_TEMPLATE=./nginx/prod-http.conf.template \
       docker compose up -d --build backend frontend nginx
   ```

   `NAME=value команда` задаёт переменную только для одной команды. Здесь Nginx получает HTTP-шаблон без ссылки на ещё не существующие сертификаты.
7. Запускает Certbot и получает сертификат через HTTP-01 challenge.
8. Пересоздаёт только Nginx с обычным HTTPS-шаблоном.

### Certbot и Docker mounts

```sh
docker run --rm \
  -v "host_path:/var/www/certbot" \
  -v "/etc/letsencrypt:/etc/letsencrypt" \
  certbot/certbot:v5.7.0 certonly --webroot ...
```

- `docker run` запускает одноразовый контейнер напрямую, не Compose-сервис.
- `--rm` удаляет контейнер после завершения, но **не** удаляет примонтированные файлы сертификата.
- `-v host:container` монтирует путь с VPS в контейнер. Суффикс `:ro` в Compose означает read-only; у Certbot `:ro` нет, потому что он должен записать сертификат.
- `certonly` получает сертификат, но не пытается сам менять Nginx.
- `--webroot` кладёт проверочный файл в `/var/www/certbot`; Nginx отдаёт его по `/.well-known/acme-challenge/`.
- `--domain` передаёт домен из `NGINX_SERVER_NAME`; DNS уже должен вести на VPS.
- `--agree-tos` принимает условия Let's Encrypt, `--no-eff-email` отключает маркетинговые письма.

Если DNS ещё не обновился, порт `80` закрыт firewall'ом или другой веб-сервер занял порт, Certbot завершится ошибкой. Это нормально: исправляем причину и запускаем скрипт заново.

## `deploy.sh`: обычный релиз

Запускать после `git pull`, когда `.env` уже существует:

```sh
sh scripts/prod/deploy.sh
```

### Шаг 1. Сохранение предыдущих образов

```sh
image_id=$(docker compose images -q "$service")
docker image tag "$image_id" "fullstack_exemplary_app-$service:$rollback_tag"
```

- `docker compose images -q backend` печатает только ID текущего образа (`-q` = quiet).
- Если образ существует, ему добавляется тег с UTC-временем. Это локальная точка возврата для образов frontend/backend.
- Это **не автоматический rollback**: скрипт только сохраняет старую версию. Откат нужно делать осознанно отдельной командой после диагностики.

### Шаг 2. Сборка

```sh
docker compose build backend frontend
```

Собираются только образы, в которых есть новый код. PostgreSQL и Nginx здесь не пересобираются. На VPS с 4 ГБ RAM сборка может потреблять заметно больше памяти, чем работа готовых контейнеров; swap полезен как страховка, но не делает сборку быстрой.

### Шаг 3. Бэкап и миграция

```sh
docker compose --profile tools run --rm backup
docker compose --profile tools run --rm migration
```

- `--profile tools` включает сервисы, которые обычно выключены.
- `run` создаёт отдельный контейнер именно для одной команды, не запускает его как постоянный сервис.
- `--rm` удаляет завершившийся контейнер. Данные БД не удаляются: они находятся в `postgres_data`, а дамп — в S3.

Сначала делается бэкап, потом миграция. Если миграция падает, `set -e` прекращает релиз до перезапуска нового backend/frontend.

### Шаг 4. Перезапуск приложения

```sh
docker compose up -d --no-deps --force-recreate backend frontend
docker compose up -d nginx
```

- `up -d` запускает контейнеры в фоне (*detached*), чтобы shell не был занят логами.
- `--no-deps` не перезапускает зависимости backend/frontend, то есть PostgreSQL остаётся работать.
- `--force-recreate` создаёт новые контейнеры даже если Compose считает, что конфигурация не изменилась. Так гарантированно используется новый образ.
- Вторая команда запускает/обновляет Nginx обычным способом. Если изменений нет, он не обязательно будет пересоздан.

### Шаг 5. Проверка готовности

```sh
docker compose exec -T backend node -e 'fetch(.../api/health/ready)...'
```

- `exec` запускает команду **в уже работающем** backend-контейнере.
- `-T` отключает виртуальный терминал (TTY). Это нужно для неинтерактивного скрипта и cron/CI.
- `node -e '...'` исполняет короткий JavaScript без отдельного файла.
- `/api/health/ready` проверяет, что backend отвечает и может подключиться к PostgreSQL. Ненулевой результат завершит deploy с ошибкой.

Сообщение `Deployment succeeded` означает, что все эти этапы прошли. Оно не заменяет ручную проверку страницы после значительных UI-изменений.

## `renew-tls.sh`: продление сертификата

Let's Encrypt-сертификаты короткоживущие, поэтому этот скрипт запускают регулярно. Пример cron от root:

```cron
17 3 * * * cd /path/to/fullstack_exemplary_app && /bin/sh scripts/prod/renew-tls.sh >> /var/log/fullstack-tls-renew.log 2>&1
```

Значения здесь означают: каждый день в 03:17 перейти в репозиторий, запустить скрипт и дописать stdout/stderr в лог. Путь `/path/to/...` нужно заменить на настоящий путь на VPS.

Скрипт:

1. Удаляет marker-файл `.certbot-renewed` через `rm -f` (`-f` не ругается, если файла нет).
2. Выполняет `certbot renew`. Certbot сам понимает, какой сертификат действительно пора продлевать.
3. Передаёт `--deploy-hook "touch ..."`: `touch` создаст marker только если сертификат был реально обновлён.
4. Если marker существует (`[ -f ... ]`), удаляет его и выполняет `nginx -s reload` внутри nginx-контейнера. Reload перечитывает сертификат без остановки сервера.

## Бэкапы: `ops/backup/backup.sh`

Сервис `backup` использует образ PostgreSQL: в нём уже есть `pg_dump`, `pg_restore`, `createdb`. Dockerfile добавляет AWS CLI и назначает `backup.sh` entrypoint — команду, которая запускается по умолчанию.

### Создание дампа

```sh
pg_dump --format custom --compress 9 --no-owner --no-privileges --file "$backup_file"
```

- `pg_dump` читает PostgreSQL и создаёт дамп.
- `--format custom` — формат для `pg_restore`; он удобнее SQL-текста для выборочного восстановления.
- `--compress 9` — максимальное сжатие, экономит S3 и сеть ценой CPU.
- `--no-owner` и `--no-privileges` не пытаются восстановить владельцев/ACL из старого окружения.
- `PGPASSWORD` экспортируется только внутрь backup-контейнера, чтобы PostgreSQL CLI могла аутентифицироваться без интерактивного пароля. Не выводи эту переменную в лог.

### S3 и хранение

После создания один дамп загружается в S3 как daily. По воскресеньям добавляется weekly, первого числа месяца — monthly.

| Набор | Сколько хранится |
| --- | ---: |
| `daily` | 7 последних |
| `weekly` | 4 последних |
| `monthly` | 6 последних |

Функция `prune_backups` запрашивает ключи в S3, сортирует их по ISO-времени в имени и удаляет самые старые сверх лимита. Поэтому корректность времени VPS важна.

Функция

```sh
s3() { aws --endpoint-url "$BACKUP_S3_ENDPOINT" "$@"; }
```

— это shell-функция-обёртка. `$@` передаёт все аргументы дальше без потери их границ; так не нужно повторять endpoint в каждой AWS-команде.

## `restore-backup.sh`: восстановление без уничтожения production

Этот сценарий специально **не** восстанавливает бэкап поверх основной БД. Он требует отдельное имя БД:

```sh
RESTORE_S3_KEY='postgres/daily/2026-08-03T03-17-00Z.dump' \
RESTORE_DB_NAME='restore_check_20260803' \
sh scripts/prod/restore-backup.sh
```

Скрипт откажется работать, если `RESTORE_DB_NAME` равна `DB_NAME`:

```text
Refusing to restore over DB_NAME; use a separate RESTORE_DB_NAME.
```

Внутри одноразового backup-контейнера он:

1. скачивает выбранный S3-объект во временный файл;
2. создаёт `RESTORE_DB_NAME` командой `createdb`;
3. применяет дамп командой `pg_restore`;
4. удаляет временный файл через `trap`.

### Почему там `--entrypoint sh` и `-ec '...'`

У backup-образа entrypoint — `backup.sh`. Но для восстановления нужен другой shell-код, поэтому `--entrypoint sh` временно заменяет стартовую команду контейнера.

- `-e` у `sh` — остановиться на ошибке;
- `-c 'текст'` — выполнить переданный текст как shell-скрипт;
- `-e VAR=value` в `docker compose run` передаёт одну переменную окружения внутрь контейнера.

Внешний shell использует одинарные кавычки вокруг большого блока, чтобы `$backup_file`, `$DB_PASSWORD` и остальные переменные раскрылись **внутри контейнера**, а не на VPS до его запуска.

## Полезные диагностические команды

Все команды выполняй в корне репозитория на VPS:

```sh
# Состояние контейнеров
docker compose ps

# Логи конкретного сервиса; -f означает follow, Ctrl+C только прекращает просмотр
docker compose logs -f backend
docker compose logs -f nginx

# Проверить готовность backend вручную
docker compose exec -T backend node -e \
  'fetch("http://127.0.0.1:3000/api/health/ready").then(r => process.exit(r.ok ? 0 : 1))'

# Список backup-объектов в S3 — только если AWS CLI и переменные настроены
docker compose --profile tools run --rm --entrypoint sh backup -ec \
  'aws --endpoint-url "$BACKUP_S3_ENDPOINT" s3 ls "s3://$BACKUP_S3_BUCKET/$BACKUP_S3_PREFIX/" --recursive'

# Размер Docker-образов, контейнеров и volumes
docker system df
```

Не запускай `docker compose down -v` на production VPS: флаг `-v` удаляет именованные volumes, включая `postgres_data` с рабочей БД.

## Что скрипты намеренно не делают

- Не выполняют `git pull` и не создают Git-коммиты.
- Не печатают `.env`, пароли, JWT, S3-ключи или содержимое дампа.
- Не делают автоматический откат после проблем с новой версией.
- Не восстанавливают дамп поверх production БД.
- Не настраивают firewall, DNS, Docker и SSH на чистом VPS: это отдельный первый этап настройки сервера.

Если перед запуском команды непонятно, что она изменит, остановись и сначала посмотри состояние через `docker compose ps`, логи и `git status`.
